# 数据与业务契约

reviews 仅覆盖实际复核，缺失不是支持或否定。supported 指现有材料支持申报，不保证不存在其他异常。permissions 记录合法共用代办原因。presence 是本地合成签到，只用于审核分析，不包含真实个人信息。

## 数据集合

- `claims`：主键为 `claim`；必填字段 `claim, school, session, teacher, agent, venue, amount, attachments`，当前 36 条。
- `presence`：主键为 `record`；必填字段 `record, claim, person, minutes, source`，当前 378 条。
- `reviews`：主键为 `claim`；必填字段 `claim, reviewed_at, outcome, selection`；可选 `selection_probability`，当前 12 条。
- `policies`：主键为 `policy`；必填字段 `policy, amount_threshold, daily_budget`；可选 `max_group_share`（默认 0.4）和 `max_group_size`（默认 8）。
- `permissions`：主键为 `agent`；必填字段 `agent, reason, valid_from`，当前 1 条。
- `reviewers`：主键为 `reviewer`；必填字段 `reviewer`；可选 `capacity`（每日名额）、`conflicts`（学校列表）和 `conflicts_by_field`（按 `school/teacher/agent/venue/session` 列出的利益关联值）。

集合中的主键不得重复；schema 的 foreign 引用须指向已存在的记录。可空字段保留 null 的业务含义，不自动补零。

## 查询与材料

GET 查询使用 UTF-8 JSON，错误参数返回 400，不存在的接口返回 404。重复的单值参数视为无效。summary 与 HTTP 调用同一组只读计算，材料包含数据内容指纹和生成时间，便于核对输入。查询不写回数据，可重复运行。

主要查询：

- `/api/checks`、`/api/queue`：保留原有的逐笔检查与按金额队列。
- `/api/leads`：关联线索分组、班次风险、理由与保留意见（caveats）。`scope=all|open` 控制是否包含已复核班次。
- `/api/plan`：每日复核清单，含组内名额上限和被延后的班次及原因。
- `/api/leads/evaluation`：新旧排序的反馈来源与选择偏差说明。

## 关联线索

线索只作为“需要一起查看”的理由，不作违规认定，不作出处罚决定，也不读取外部个人资料。

- 只在跨校班次之间寻找线索；同校续班不单独作为线索。
- 至少两个独立关系族（教师、代办人、场地、班次编号、到场名单重合）才可能成组；共用代办人或场地很常见，单独一条不构成线索。
- 到场名单按较小名单的重合比例计算；缺失签到记录不等于套领。
- 单笔附件缺失、负金额只作为次要检查项和保留意见，不单独把班次变成高风险。
- 分组设上限（`max_group_size`），超出上限的合并会记录在 `suppressed_links`，不会静默丢失。

## 复核清单与名额

- 同一关联组每天最多占 `floor(daily_budget × max_group_share)` 个名额，至少 1 个。
- 被组内限流或日名额挤出的班次列在 `deferred` 中，保留风险与原因，不会因合并而隐藏高风险班次。
- 已复核班次不进入清单；审核员回避的班次保持待复核，回避释放当日名额。
- 组内部分完成只调整剩余班次的关联依据与名额，不连带结案未复核班次。

## 派工与索件

- `review_dispatch.assign`：按笔派工，逐笔检查学校及教师、代办人、场地的利益关联；涉及关联组时避开组内所有待复核成员的利益关联。
- `review_dispatch.dispatch`：按线索顺序批量派工，遇利益关联、名额不足或组内限流时继续尝试后续班次，跳过原因全部返回。
- `review_dispatch.recuse`：登记回避原因，释放名额，班次仍待复核；可指定 replacement 重新派工。
- `document_requests.request`：向本校索取该笔或该校在关联组中的签到记录。
- `document_requests.request_group`：多校关联组按学校分别索件，每校只收到本校签到明细，其他学校只给出汇总数量；重复调用返回同一份请求。
- `review_feedback.resolve`：登记单笔复核结论，只结这一笔；同组其他班次仍需单独派工与复核。

业务操作以 JSON 对象 POST 到 `/api/workflow/操作名`，现有函数入参和行为保留。
`review_dispatch.assign`、`document_requests.request`、`review_feedback.resolve` 的既有用法兼容，
新增 `review_dispatch.dispatch`、`review_dispatch.recuse`、`document_requests.request_group`。

## 评估与选择偏差

历史复核只来自审核员挑中过的样本（示例数据均为 `large_amount`），未复核班次不是负例：

- 默认只在历史已复核子集内比较新旧排序（`reviewed_stratum`），避免把旧的挑选习惯学得更牢。
- 未复核班次保留为未知，不进入支持/否定计数。
- `selection` 与 `selection_probability` 保留用于后续按概率加权、分层比较；未记录抽选概率时不做总体推断。
- `feedback_source` 保留旧排序名次与新排序名次，作为比较新旧排序价值的稳定反馈来源。
- 评估只比较排序价值，不参与评分，不据此处罚。

## 现有办理协作

每个操作在本地业务日志的事务中更新；失败不提交半条办理记录。已有人工流程可以继续使用。
接口传入业务标识，未知标识或不满足条件返回错误，不自动补建对象。
